## 1. Cross-Platform Companion App (Android + Windows / Linux / macOS)

### 1.1 Why One Codebase for Both Mobile & Desktop (`Tauri v2` + Rust Core + `@vaiev/ui`)
Instead of maintaining separate Android (Kotlin) and Desktop (C++/Electron) stacks, Sidged shares a single **Tauri v2** shell wrapping:
1. **Rust Core Libraries (`sidged-core`, `sidged-grant`, `sidged-verify`, `sidged-log`, `sidged-cli::swarm`):** Compiled natively into the Android APK (`aarch64-linux-android`) and Desktop binaries (`x86_64`/`aarch64` for Linux, Windows, macOS).
2. **Dual Role per Device:**
   - **Remote Approver & A2UI Surface Mode:** Connects to the owner's primary Edge 1 (VM / Home Server / Cloud VPS), renders Core-verified A2UI surfaces, and signs Trusted UI approvals (`0004 R9`) using hardware-backed keys.
   - **Local Swarm Worker Mode (`Edge 2..n`):** On Desktop (Windows/Linux/macOS) or high-end Android, the app can also execute delegated non-consequential capabilities (`0015 S9`) using local CPU inference (`Qwen3-0.6B` `q8_0`).

## 2. Zero-Trust Pairing & Verification via QR, Passkey & `swiyu-admin-ch`

### 2.1 Alignment with Swiss E-ID Open Source Ecosystem (`swiyu-admin-ch`)
The Swiss Federal E-ID infrastructure (`https://github.com/swiyu-admin-ch`) uses **OpenID4VP**, **SD-JWT VC**, **DID (`did:tdw` / `did:webvh` / `did:key`)**, and **Hardware Key Binding (Android Keystore / StrongBox / Secure Enclave / WebAuthn Passkeys)**.

Sidged integrates this directly in `runtime/sidged-cli/src/swarm.rs` (`QrPairingInvite` & `VerifiablePairingPresentation`):
1. **Short-Lived Signed QR Invite (`sdg://pair/v0?invite=<base64url>`):**
   - Generated by Edge 1 (`create_qr_pairing_invite`), binding `edge1_did`, `image_digest`, a 256-bit `challenge`, `tunnel_mode`, and a max 300-second expiry signed with domain separation `"sdg.qr.pair/v0\0"`.
2. **Three Supported Verifiable Presentation Formats (`VerifiablePairingPresentation`):**
   - `"sdg-didkey-vp"`: Native Ed25519 `did:key` proof-of-possession.
   - `"webauthn-passkey"`: FIDO2/Passkey hardware-bound key attestation.
   - `"swiyu-sd-jwt-vc"`: Holder-bound presentation verified against `swiyu` ecosystem trust anchors (`issuer_attestation`), enabling high-assurance identity binding for sovereign and regulated deployments without exposing unnecessary personal attributes (selective disclosure).

### 2.2 End-to-End Encrypted Tunneling (`Cloud <-> Local` and `Local <-> Web <-> Local`)
To satisfy **Spec 0010 §3 (Zero Public Ports)** even across NAT/CGNAT and mobile networks:
- **`local-direct`:** Direct LAN / Unix socket / WireGuard link.
- **`cloud-to-local-e2ee`:** Outbound-only connection from the local Home VM to a stateless blind relay (`CH` residency). The relay forwards only opaque Noise/QUIC + Ed25519-signed `SwarmEnvelope` ciphertext (`0006` / `0015`). The relay has **zero** access to keys or plaintext.
- **`local-to-web-to-local-e2ee`:** Ephemeral WebRTC DataChannel / WebTransport rendezvous between two local devices (e.g., Android App ↔ Home VM or Laptop ↔ Home VM) negotiated via an untrusted signaling rendezvous, where mutual authentication and payload encryption are enforced end-to-end by `connect_and_handshake` (`sdg.handshake/v0\0`) before any frame is accepted.

## 3. Modular Responsive UI Generation with `@vaiev/ui` (`components-v4`)

### 3.1 Pre-Vetted Glassmorphic-Material Component Registry + LLM Composition
Rather than letting an LLM generate arbitrary HTML/CSS/JS (which violates Invariants 1, 3, and 4), Sidged pairs a **curated, responsive component catalog from `vaiev/ui/components-v4`** (VAIEV Glassmorphism + Material 3 token system) with the local Edge LLM (`Model 0` + `Model 1`):

| Component Category | `@vaiev/ui` (`components-v4`) Primitives | LLM Role (`Model 0` / `Model 1`) | Core Enforcement |
| :--- | :--- | :--- | :--- |
| **Core v1 Registry** | `TaskList`, `CountdownWidget`, `NoteEditor`, `WebResult`, `CloudCallTrace` | Selects component + populates typed JSON `props` | Validates schema, strips forbidden keys (`residency`, `grant`, `approve`) |
| **Extended v4 Data & Layout** | `GlassCard`, `SplitPane`, `KanbanBoard`, `DataTable`, `TimelineFeed`, `MetricSpark`, `KeyValueGrid` | Composes responsive multi-card layouts per user intent | Enforces `--vv-*` token whitelist, max 1 `.vv-glass` layer, 48px touch targets, WCAG AA contrast |
| **Interactive Intents** | `ActionChipBar`, `FilterBar`, `FormSheet` (non-approval) | Binds button/form triggers to verified `urn:sidged:capability:*` IDs | Every triggered capability goes through `sidged-verify` + `sidged-grant` + Trusted UI approval |

## 4. ISO/IEC 27090 (AI Cybersecurity) Compliance Mapping

Sidged's architecture maps directly to **ISO/IEC 27090** (*Cybersecurity — Artificial Intelligence — Guidance for addressing security threats and failures in AI systems*):

| ISO/IEC 27090 Threat / Control Area | Sidged Mechanism & Code Location |
| :--- | :--- |
| **1. Prompt Injection & Indirect Injection Containment** | Invariant 1 & 3: External/model/web inputs are untrusted data until verified by `sidged-verify` (static DAG + CEL check without comprehension macros) and `CedarFlowPolicy` (`runtime/sidged-verify/src/flow.rs`). |
| **2. Model Hallucination & Faulty Actuation Prevention** | Technocratic Swarm Culling (`verify_worker_proposal_or_cull_and_replace` in `runtime/sidged-cli/src/swarm.rs`): A worker that hallucinates capabilities or violates IFC is immediately revoked, audited (`swarm_worker_culled`), and replaced by a fresh instance. |
| **3. Training Data & Weight Supply-Chain Provenance** | Deterministic dataset generator (`make_dataset.py`), PII/secret/IP validator (`validate_dataset.py`), pinned 40-hex base-model commit SHA, and SHA-256 provenance manifest (`write_manifest.py`). |
| **4. Data Exfiltration & Residency Enforcement** | Spec 0013 §4 R10 (`secrets.*` never reach egress even with owner permit) + Spec 0007 Privacy Gateway (`runtime/sidged-gateway/src/send.rs`: fail-closed residency `CH`/`EU` vs. `GLOBAL`, `sdg.pii/1` R13 scrubbing). |
| **5. Human-in-the-Loop Integrity (Anti-Spoofing)** | Spec 0004 R9/R9c (`runtime/sidged-cli/src/approval.rs`): Consequential steps require approval over a kernel `SO_PEERCRED`-verified Unix socket from a dedicated `sidged-approver` UID (`65540`) with fail-closed `sudoers`/`doas` and `/proc` ptrace checks. |
| **6. Cryptographic Non-Repudiation & Tamper Evidence** | Spec 0005 / 0012 (`runtime/sidged-log`, `runtime/sidged-record`): Pre-effect Ed25519-signed SHA-256 hash chain for every allow/deny decision and canonical dCBOR signed records. |

# 0003 – Plan language v0 (SDG-L3)

> **Status:** Draft v0.1. The verifier in `runtime/sidged-verify` implements the rules below.
> **Date:** 2026-10-14
> **Spec:** SDG-L3 Plan
> **Basis:** [0000-architektur.md](0000-architektur.md) plan-language v0, accepted with question 4 on 2026-10-14, and [0001-capability.md](0001-capability.md).

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as in BCP 14 (RFC 2119 and RFC 8174) when they appear in capitals.

A plan is a JSON document a model may write. The Core verifies it before any step runs. The verifier's result is the security decision. The model is not.

## 1. Document

The shape is [plan.schema.json](../../spec/schemas/plan.schema.json). `v` MUST be `"0.1"`.

A plan has an optional `goal` string, an optional money `budget.max`, and one to 32 `steps`. Step ids are lowercase identifiers, unique in the plan. A step is a `call`, an `expr`, or a `map`.

An argument is one of:

| Form | Meaning |
|---|---|
| `{ "lit": <string, number, bool, or null> }` | A constant. It carries no data-class label. |
| `{ "ref": "<earlier step id>" }` | The output of that step, with that step's labels. |
| `{ "ref": "<earlier step id>", "field": "<name>" }` | Member `<name>` of that step's output (R4a), with that step's labels. |
| `{ "item": true }` | Inside a `map` only. The current element, with the labels of the list being mapped. |

**R1.** A consumer MUST reject a plan whose `v` it does not implement. *Rationale: an unknown plan shape is not verified.*

**R2.** A plan MUST contain at most 32 steps, and step ids MUST be unique. *Rationale: the effect set has to stay readable in one approval.*

## 2. Steps

**R3.** A `call` or a `map` MUST name a capability id the verifier knows from the catalog passed in with the plan. The catalog entry MUST include `effects`, `data_classes`, `consequential`, and `cost`. *Rationale: effects come from the capability, not from the model's prose.*

**R4.** A `ref` MUST name an earlier step. It MUST NOT name the current step or a later one. *Rationale: the graph is ordered. There is no recursion in v0.*

**R4a.** *Explicit projection (lead decision 2026-10-23, ROADMAP 11f).* A `ref` with `field` MUST name a property that the referenced capability's `output_schema` declares; a verifier MUST reject any other name. The executor MUST pass exactly the referenced value: the whole output for a bare `ref`, that member for a `ref` with `field`, never a value it picks by guessing (another member, a default member, a serialisation of the whole output). If the value does not satisfy the consuming capability's `input_schema`, the step MUST be refused. *Rationale: the verifier labels and checks what the plan says flows; an executor that chooses a different value at run time executes a plan nobody verified.*

**R5.** `{ "item": true }` MUST appear only in the `args` of a `map`. *Rationale: there is no current element outside a bounded map.*

**R6.** A `map` MUST set `bound` to an integer from 1 to 32, and `over` MUST be a `ref` to an earlier step. *Rationale: question 4 allows `map` only with an explicit upper bound. 32 is the v0.1 cap so cost and effects stay finite.*

**R7.** A step whose capability has `consequential: true` MUST set `approval` to `true`. One approval on a `map` covers each repetition up to `bound`. *Rationale: invariant 4. The owner sees the bound. The model cannot skip the approval by omitting the flag.*

## 3. CEL expressions

An `expr` step's `expr` string is CEL (Common Expression Language). v0.1 does not define a Sidged expression language (E6).

**R8.** The expression MUST parse as CEL. *Rationale: the verifier rejects a string it cannot read. The `cel` crate 0.15 (cel-rust) compiles the string; a parse error is a refusal, never a crash. It is a dependency because a hand-written dialect would be the language E6 rejected. No host functions are registered, so a plan expression cannot call the network or the filesystem.*

**R8a.** An expression MUST be at most 1024 characters and MUST NOT nest brackets (`(`, `[`, `{`) more than 4 levels deep. Brackets are counted everywhere in the string, string literals included. A verifier MUST check both bounds before it parses the expression. *Rationale: CEL parsers recurse per bracket level. The reference parser overflows the stack (an abort, which a verifier cannot catch) from about 8 levels in a debug build on a 1 MiB stack, and a browser verifier has no more. Plan v0 expressions select fields (`free.slots`) and need no deep nesting. Counting inside literals keeps the bound independent of how a verifier lexes strings.*

**R9.** The only variables in the expression MUST be ids of earlier steps. Comprehension macros (`filter`, `map`, `all`, `exists`, `exists_one`) MUST NOT appear. *Rationale: a macro is a hidden loop. The bounded `map` step is the only loop in v0. Field selection (`free.slots`) is allowed. The variable is `free`.*

The expression is not executed during verification. Labels flow from the variables it names. Running the expression is a later runtime step, after verification.

## 4. Effects and labels

The verifier computes, before execution, the set of capability ids, the data classes that flow, the egress capabilities, the steps that need approval, and the maximum cost.

**R10.** The output labels of a `call` or `map` are the capability's `data_classes` plus the labels of its arguments. A `map` also carries the labels of the list it maps over (`over`), whether or not an argument is the item. The output labels of an `expr` are the labels of the steps it names. A `lit` has no labels. *Rationale: labels travel with values. The verifier does not need the runtime values. How often a `map` runs its capability depends on the list, so a `map` over health records that sends one fixed message per element still reveals how many records there are (an implicit flow); the Cedar stage (0013 R8) already counted it, and the label computation now agrees.*

**R11.** A class reaches an `egress` capability when it is on an argument or on that capability's own `data_classes`. `health.records`, `secrets`, and any subclass of either (`health.records.notes`, `secrets.token`) MUST NOT reach an egress capability unless the flow policy allows that class for that capability id. *Rationale: this is the information-flow check from the architecture. The default policy denies. `sidged-grant` evaluates a Cedar fragment for grants (`0002-grant.md`, `CedarEvaluator`). The plan verifier does not call that evaluator. Its hook is `FlowPolicy::allow_egress`, and the hosted verifier uses `DenySensitive`, which denies every sensitive class. A Cedar policy that replaces `DenySensitive` for this flow is later SDG-L3 work (roadmap phase 18). The shared vectors use the default denial, plus one vector that passes an explicit allow list so the hook is visible.*

**R12.** The effect set of the plan is the union of the effects of each `call` and each `map`. A `map` contributes its capability's effects once. The summary MUST list every capability id the plan can invoke. *Rationale: the Core shows this summary. It is not optional prose.*

## 5. Cost

**R13.** A `free` capability costs zero. A `metered` capability costs its `cost.max`. A `map` costs that amount times `bound`. The sum is the plan's maximum cost. *Rationale: the bound is the worst case. The verifier does not guess how many elements exist.*

**R14.** When any step is `metered`, the plan MUST have `budget.max` in the same currency, and the maximum cost MUST be less than or equal to `budget.max.amount`, compared as an exact decimal. *Rationale: the owner caps spend before the plan runs. Dropping the currency or using binary floats would hide a larger amount.*

## 6. Conformance

`plan-check` vectors live in [spec/test-vectors/plan/verify.json](../../spec/test-vectors/plan/verify.json). The input is the plan, the capability catalog, and an optional `allow` list of `{ "class", "capability" }`. The Python checker and `sidged-verify` both accept or refuse. A vector with `"requires": ["cel"]` is the CEL parser check. The Python checker skips it. `sidged-verify` runs it.

An allowed plan in the suite reads calendar availability and sends a message with `approval: true`. A rejected plan pushes `health.records` into an egress capability, omits an approval, maps with `bound` 100, references a later step, or exceeds the budget.

## 7. Out of scope

- General recursion, unbounded loops, and CEL comprehension macros.
- A normative text syntax for humans. The v0.1 verifier's interchange form is JSON. Deterministic CBOR (`dcbor`) is an L0 canonical encoding of the same tree (`0000-architektur.md`, SDG-L0), including when a plan is signed or stored. SDG-L6 does not define that encoding. An L6 envelope carries bytes that are already in an L0 encoding. A v0.1 verifier MAY reject a CBOR plan it does not implement. Checking `dcbor` plans is roadmap phase 18.
- Compiling a plan to WASM. A step that needs arbitrary computation names a module, which is not a plan step in v0.1.
- Multi-party negotiation inside a plan.
- Executing the plan, issuing grants, drawing Trusted UI, or filing the MCP SEP.
- Replacing `DenySensitive` with a Cedar flow policy. Grant checks already use the Cedar fragment in `sidged-grant`. Until that replacement, the plan hook is `FlowPolicy`.
- Signature verification of a stored plan.

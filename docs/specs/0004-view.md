# 0004 – View and Trusted UI (VKR-L4)

> **Status:** Draft v0.1. The hosted approval channel (section 2.1, R8–R12) and the static A2UI + `ResultSurface` shell (`ui/shell/`) are implemented.
> **Date:** 2026-10-15
> **Spec:** VKR-L4 View
> **Basis:** [VISION.md](../vision/VISION.md) sections 1, 2, and 4, and the L4 design section of [0000-architektur.md](0000-architektur.md).

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as in BCP 14 (RFC 2119 and RFC 8174) when they appear in capitals.

A view is the surface for one task. Trusted UI is the set of controls the Core draws itself. A generated view is not a module and it is not a grant.

## 1. Generated view

**R1.** A view MUST be declarative. It MUST NOT carry executable code, a script, or a WASM module. *Rationale: foreign code belongs in a module (invariant 6). A view that runs code would put that code in the interface, outside the sandbox.*

**R2.** The runtime MUST be able to generate a view per task. The same task MAY differ by device and by person. *Rationale: the vision generates the surface for the intent in front of the owner. One toolkit for every task is the userland this layer replaces.*

**R3.** The binding for a generated view MUST be A2UI. Vaikor MUST NOT define a second generated-UI protocol. *Rationale: E1. Option C adopts A2UI. The Core still decides what of that view may be shown.*

## 2. Trusted UI

**R4.** Approvals, the kill switch, and the residency indicator MUST be drawn on a Trusted UI channel the Core owns. *Rationale: invariant 4. The owner has to see a control the model cannot restyle.*

**R5.** A generated view MUST NOT paint over, cover, or restyle a Trusted UI element. *Rationale: an unbreakable channel is the point of keeping Trusted UI in the Core. L8's compositor is what makes this unforgeable on the native image. The rule holds on the hosted runtime as well.*

**R6.** A voice approval MUST include a step a synthetic voice cannot satisfy. *Rationale: accepted with invariant 4 in `0000-architektur.md`. A model that can speak must not be able to approve its own consequential step.*

### 2.1 Hosted approval channel

The hosted runtime has no compositor. Its Trusted UI is a channel the Core reads itself. A GUI approval sheet (`TrustedApprovalSheet`) can only be a front end to the R9 Unix socket channel.

**R8.** A consequential step MUST NOT run until this channel returns an explicit approval. No answer, a deny, a timeout, and the kill switch MUST be denials. *Rationale: invariant 4. `approval: true` on a plan is the verifier flag. It is not the person.*

**R8a.** *Standing approval for model calls (owner decision, roenu, 2026-10-15).* A remote model or planner call is the only exception to R8. After one explicit owner approval on this channel for a pair (`provider`, `task_type`), the Core MAY run later calls for that pair without a new prompt. This holds only while the standing approval has a limit and an expiry, is unexpired, and the call stays within that limit (spec 0007 R8–R8b). The first approval and every call over the limit MUST use R8–R9. The exception never covers a capability step with an effect other than the model call itself, and never overrides 0007 R9 or §5.3. *Rationale: invariant 4 is kept for the decision to export to a provider. The limit, not a prompt per call, bounds repeated use.*

**R9.** When the process has no approval channel, the Core MUST deny. Each request binds the step id, capability, SHA-256 digest of canonical JSON arguments, a fresh random single-use nonce, and the plan digest (0013 R2: SHA-256 of dCBOR, unpadded base64url). The only approval channel is the hosted Unix socket (`--approve unix:<path>`); there is no TTY or `/dev/tty` channel and no HTTP channel. It accepts `approve <who> <step> <capability> <args_sha256> <nonce> <plan_digest>` or `deny` with the same fields. The socket: the operator provisions only its directory; the Core creates the socket in it and validates both (R9c). It MUST authenticate every connection server-side using Linux `SO_PEERCRED` and accept only connections whose peer uid equals the configured approver uid (`--approve-uid <uid>`, mandatory; no default). Credential lookup failures MUST refuse the connection. The response MUST echo every binding field exactly. A response carrying a stale or other nonce MUST be audited with decision `deny` and reason `stale approval response`, discarded, and the channel MUST continue waiting for the current nonce until the original deadline. A mismatch in other fields of a current-nonce response, nonce replay, or timeout MUST deny. Every request nonce is consumed on approval, denial, or timeout. The nonce MUST NOT be printed to stdout/stderr or included in logs; the launcher prints only the approval socket path. *Rationale: non-interactive mode must not approve, and a late response must not decide the next request.*

*R9 (amendment, owner decision roenu 2026-10-16, v1 spec).* The hosted socket channel MUST require `--approve-uid <uid>` with an explicit value. If the option or its value is missing, the Core MUST refuse to start the channel and deny as for "no approval channel" above. It MUST NOT default to the Core's effective uid. A consequential step MUST be approved by a separate approver uid on every channel: the approver uid MUST differ from the effective uid of the Core, the launcher, and every agent, model, planner, and worker process. There is no same-uid exception. Local mode (`VAIKOR_LOCAL=1`, `--local`, or `config.local = true`, 0007 R2) has no approval channel; consequential steps are denied there. `VAIKOR_LOCAL=1`: no listening socket (0 bind/listen), no egress, at most one outbound connect to the statically configured local model endpoint. The model endpoint is `AF_UNIX` by default, with an `SO_PEERCRED` check against the configured model uid; if that endpoint fails, the model connect is refused (fail-closed). `127.0.0.1:<port>` is used only when the operator explicitly configures it (`model.endpoint` set to a TCP loopback address); the Core never falls back to it automatically, and the audit start record marks it. Risk of that fallback: prompts, including `local-only` data (0007 R9), go to whatever local process holds the port, with no peer check. Integrity still holds because model output stays untrusted (schema/GBNF) and every tool call still goes through grant, Cedar, and approval, so a fake endpoint cannot cause any effect without a grant. `--approve unix:<path>` together with local mode MUST refuse to start. Offline capability (invariant 7) is not local mode: normal mode with a local `AF_UNIX` approval socket and no egress (no network, or the gateway with no reachable destination, which fails closed per 0007 R3) is fully offline-capable; local mode is the profile with no listening socket and only the local model connect, without consequential steps. The v1 DoD demo approves in normal mode. If the configured approver uid equals any of those uids, the Core MUST refuse to start the approval channel and deny as for "no approval channel" above. Agent, model, planner, and worker processes MUST NOT run under the approver uid.

*R9d (amendment, owner decision roenu 2026-10-20).* Outside local mode the Core MAY also use the statically configured local model endpoint when it is `AF_UNIX` with the `SO_PEERCRED` check against the configured model uid. That connect is not egress: nothing leaves the device, so there is no Privacy Gateway reservation and no residency decision (0007), and it is not a listening socket. Each model call uses one client that connects at most once; the reply stays untrusted and every effect still needs schema checks, the verifier, a grant, Cedar and approval. A TCP loopback endpoint MUST NOT be used outside local mode, because it has no peer check. The model process MUST NOT run under the approver uid (R9, R9c). Local mode keeps its stricter profile (no listening socket, no egress, no swarm mesh, 0015 S14). *Rationale: the companion linguist and the turnkey path run Model -1 on the owner's device while the node also plans and joins its owner's swarm (0017).*

*R9c (uid separation, provisioning, start checks).* **Uids.** The Core runs under its own core uid. Every non-approver uid (agent, launcher, worker, and model/llama processes) is configured explicitly, and every R9c check below applies to each of them. The non-approver uids are configured with `--non-approver-uid <uid>` (repeatable; `--agent-uid` is an alias) or the config key `approval.non_approver_uids`; if the list is empty or missing, the Core MUST refuse the approval channel (fail-closed). Uid checks cover the real, effective, and saved uid. The Core checks the configured uids plus its real parent process; processes started later are covered only by the operator attestation. The Core MUST refuse to start the approval channel (fail-closed, deny) if: the core uid equals any non-approver uid or the parent-process uid; `--approve-uid` equals the core uid or is 0; any non-approver uid runs as root or has `CAP_SYS_PTRACE`; any non-approver uid is in a root-equivalent group (at least `docker`, `podman`, `lxd`, `incus`, `disk`, `libvirt`) or can access a rootful container socket (this counts as root); yama `ptrace_scope` is below 1 and the core uid is not unique to the Core; or a readable sudoers (`/etc/sudoers`, `/etc/sudoers.d/*`) or doas (`/etc/doas.conf`) rule lets any non-approver uid switch to the approver uid, the core uid, or root. **Group evidence.** Group membership for these checks and for the core/approver group rule below is taken from the account's supplementary groups (`/usr/bin/id -G <user>`) and, for already-running processes, from `Groups:` in `/proc/<pid>/status`. **Helper invocation.** Any helper the Core runs for these checks MUST be called by absolute path with a cleared environment and a fixed `PATH=/usr/sbin:/usr/bin:/sbin:/bin`; never resolved through the inherited `PATH`. The spec assumes `/usr/bin/sudo` (sudo on Debian and Alpine), `/usr/bin/doas` (opendoas on Debian, doas on Alpine), and `/usr/bin/id` (coreutils on Debian, where `/bin/id` is the same file under merged-usr; BusyBox applet on Alpine). A missing `/usr/bin/id` MUST refuse the channel (fail-closed; never `operator-attested`). A missing `/usr/bin/sudo` or `/usr/bin/doas` means only that there is no executable at the assumed path; the Core still parses `/etc/sudoers`, `/etc/sudoers.d/*`, and `/etc/doas.conf` directly when present; a setuid/setgid sudo/doas copy at any other path is not detected and is covered by the operator attestation (R9c, recorded per the attestation-in-the-audit rule). A helper at any other path is not run. Otherwise yama `ptrace_scope` below 1 only produces a warning (defense in depth). The Core MUST set `PR_SET_DUMPABLE` to 0. **Provisioning.** The operator (root) provisions only the approval directory (example `/run/vaikor/approval/`), with owner = core uid, group = approver group, setgid mode 2750 or 2710. The Core validates the directory and never creates or re-owns it: owner, group, and mode as above (setgid bit set); no symlink (walk down from `/` with `openat(O_DIRECTORY|O_NOFOLLOW)` on directory fds). **Ancestors.** Every ancestor up to `/` MUST be owned by root or the core uid and MUST NOT be group- or world-writable; a sticky, `/tmp`-like ancestor is refused; an ancestor owned by any non-approver uid (agent, launcher, worker, model) is refused. **Socket.** The Core binds the socket inside that directory itself with umask 0117, so the socket is created 0660 and inherits the approver group from the setgid directory. **Umask.** The umask is process-wide: the Core MUST save the current umask, set 0117, `bind`, and restore the saved umask on every exit path (success and error), and MUST do this at startup in the single-threaded phase, before any other thread is started; a lock held only by the socket code is not sufficient. Before `listen`, the Core MUST check the socket with `fstatat(dirfd, name, AT_SYMLINK_NOFOLLOW)` (an `lstat` relative to the validated directory fd) and verify: it is a socket, owner = core uid, group = approver group, mode 0660; otherwise it MUST unlink that entry and refuse. Unlink-on-mismatch applies only to the entry this invocation just bound; a failed `bind` (for example `EADDRINUSE`) MUST NOT unlink an existing entry. A connect between `bind` and `listen` gets `ECONNREFUSED`; this is harmless because the socket already has its final owner, group, and mode at `bind` and the directory admits only the approver group. **Boot.** `/run` is a tmpfs, so the operator MUST re-create the directory at every boot (for example a `tmpfiles.d` entry `d /run/vaikor/approval 2750 <core> <approver> -`). No non-approver uid may be in the core or approver group. Any failure refuses the channel. `SO_PEERCRED` (R9) is authoritative; the directory is the second layer. **Detection limits.** These checks are not complete detection. The fail-closed cases above are clear hits only. Sudo/doas rules the Core cannot evaluate clearly (for example unparseable rules) MUST refuse the channel unless the operator starts the Core with `--operator-attest`; with that flag the channel is allowed and every approval is audited with `approval_binding: operator-attested` (R11). The label is never set automatically. Any other check that cannot be evaluated refuses the channel. The separate approver uid and the `SO_PEERCRED` check are always mandatory; `operator-attested` only records that the operator passed `--operator-attest` because the sudo/doas detection was unclear, and never replaces the uid separation. **Operator requirement (attestation):** the separation guarantee rests on the operator's R9c attestation that no other path (su with a known password, stored credentials, keys, setuid helpers, container runtimes) lets any non-approver uid (agent, launcher, worker, model) act as the approver or core uid. **Attestation in the audit.** The audit record at channel start and every approval record (R11) MUST carry `attestation: R9c` and a separate field `undetected` listing what R9c does not detect: setuid/setgid sudo/doas copies or other setuid helpers outside the standard paths, su with a known password, stored credentials, keys, and container runtimes. This field is separate from `approval_binding: operator-attested`, which only marks an explicit `--operator-attest` start after unclear sudo/doas detection. The v1 DoD demo MUST use a dedicated user `vaikor-approver` as approver uid, approving from a separate SSH session as that user.

A GUI approval sheet (`TrustedApprovalSheet`) MUST NOT be a separate approval channel: it MAY only be a front end to this R9 Unix socket channel, run by a Core-owned Trusted UI process under the approver uid and speaking exactly the R9 protocol. Generated views MUST NOT be or drive that sheet (R5, R12). Drawing the channel in a window remains out of scope until the compositor exists (§4). **Implementation status:** Enforced in `runtime/vaikor-cli/src/approval.rs` (mandatory `--approve-uid`, `SO_PEERCRED` peer uid verification, `--non-approver-uid`/`approval.non_approver_uids`, `--operator-attest`, setgid directory & `0117` umask/`fstatat` socket creation, `PR_SET_DUMPABLE=0`, and local-mode approval channel refusal). *Rationale: invariant 4. A process under the same uid can read the nonce or drive the PTY and approve its own step, so only a separate uid that agents cannot switch to keeps the approval human; a sheet must not bypass that boundary.*

**R9w.** *WebAuthn user-verification channel (owner decision roenu, 2026-10-22, WP 16).* On a device whose operating system offers a platform authenticator with user verification (Windows Hello, Touch ID, Android biometrics or device credential, a FIDO2 security key, or the owner's phone as a roaming authenticator), an approval MAY be a WebAuthn assertion instead of the R9 socket answer. The separate-uid rule of R9 does not apply to this channel, because the decision is made by the authenticator, not by a process: the operating system draws the user-verification prompt, and the key never leaves the authenticator. The rules:
- *Enrollment.* The owner registers one credential through Trusted UI at node initialisation, with user verification required. The Core stores the credential id, its public key as SubjectPublicKeyInfo (ES256 on P-256, or EdDSA on Ed25519), the relying-party id, the accepted origins, and the signature counter. A model, a bundle or a generated view MUST NOT enroll or replace a credential. Exactly one credential is enrolled; an enrollment while one is stored is refused (replacing it is a separate operator action). The bridge relays the WebAuthn Level 3 JSON form of the registration (`id`, `response.clientDataJSON`, `response.authenticatorData`, `response.publicKey` as SubjectPublicKeyInfo DER, `response.publicKeyAlgorithm`; binary fields unpadded base64url). Attestation conveyance is `none`: the Core does not evaluate an attestation statement, and trust in the credential comes from the registration being made through Trusted UI with user verification. The Core MUST accept the registration only if all of these hold: the challenge is 32 fresh random bytes issued by the Core and is consumed by this attempt, success or failure; `clientDataJSON.type` is `webauthn.create`, its `challenge` is the unpadded base64url of those bytes, its `origin` is an accepted origin and `crossOrigin` is absent or false; `authenticatorData` is at least 37 bytes, carries the SHA-256 of the relying-party id, has the user-present, user-verified and attested-credential-data flags and not the extension-data flag; the credential id is 1 to 1023 bytes and equals the decoded `id`; the credential public key is the CTAP2 canonical COSE_Key `{1: 2, 3: -7, -1: 1, -2: x, -3: y}` (ES256) or `{1: 1, 3: -8, -1: 6, -2: x}` (EdDSA) with 32-byte coordinates, no other member, and it ends exactly at the end of `authenticatorData`; `publicKeyAlgorithm` equals its algorithm; and `publicKey` encodes the same key. The stored counter is the one in `authenticatorData`. The enrollment file has mode 0600, is replaced atomically, and its counter only rises.
- *Challenge.* The challenge is the SHA-256 of the RFC 8785 JSON of the R9 binding `{plan_digest, step, capability, args_digest, nonce}`, plus `scope_digest` when R9b applies. The nonce is fresh and single-use as in R9.
- *Verification.* The Core MUST accept the assertion only if all of these hold: `clientDataJSON.type` is `webauthn.get`; its `challenge` is the unpadded base64url of that digest; its `origin` is an accepted origin and `crossOrigin` is absent or false; `authenticatorData` carries the SHA-256 of the relying-party id and has the user-present and user-verified flags; the signature counter is greater than the stored one unless both are 0; the credential id is the enrolled one; and the signature over `authenticatorData ‖ SHA-256(clientDataJSON)` verifies with the enrolled key. Any failure, a timeout or the kill switch is a denial (R8). The counter is stored after an approval.
- *Audit.* The R11 record names `approval_channel: webauthn-uv`, the credential id and the counter. `approval_binding` is `authenticator`.
*Rationale: invariant 4 on a single-user desktop or phone. Code running as the owner can ask for an assertion, but it cannot produce one without the human passing the operating system's prompt, and the challenge binds the exact step, arguments and plan; a replayed or redirected assertion fails the nonce, origin or counter check. What the prompt cannot show is the step itself, so Trusted UI (R4, WP 17) shows the step before it asks; on Android a later version SHOULD use a prompt whose text the system draws.*

**R9b.** *Standing scope.* For a first-use or over-limit remote model call (spec 0007 R8s), the request MUST also show the standing scope (provider, task_type, limit, expiry, and the explicit words "standing approval") and bind its `scope_digest` as a sixth binding field (the seventh token after `approve`): `approve <who> <step> <capability> <args_sha256> <nonce> <plan_digest> <scope_digest>`. An answer without `scope_digest`, or with a different one, approves at most that single call and never creates a standing approval.

**R10.** The line `kill` on the authenticated Unix socket MUST stop later steps. `vaikor kill unix:<path>` sends that request. *Rationale: the kill switch is a Core command, not a control inside a generated view.*

**R11.** The audit record for that step MUST say `approve` or `deny`, and MUST name who decided and when. It MUST carry the R9c fields `approval_binding` (`operator-attested` only when started with `--operator-attest`), `attestation`, and `undetected`; the audit-event schema MUST include them. It MUST NOT say `allow` for a consequential step. *Rationale: invariant 9. The log has to match what the channel did.*

**R12.** A generated view MUST NOT be accepted as this channel. *Rationale: R5. The model can propose the view. It cannot speak on the Core's channel.*

## 3. VAIEV visual rules

**R7.** Views and Trusted UI MUST follow the L4 design section of `0000-architektur.md`: content is flat, controls float, semantic tokens are `--vv-*`, a sub-brand fills `--vv-color-*` and does not invent a parallel set, WCAG 2.2 AA, hit targets at least 48 by 48 px, and honouring `prefers-reduced-motion` and `prefers-reduced-transparency`. *Rationale: those rules are already accepted. This stub points at them so L4 does not grow a second palette.*

## 4. Out of scope

- An A2UI catalogue, a schema, and test vectors. Those arrive with the phase that implements views.
- Drawing the channel in a window, including a `TrustedApprovalSheet`, until the compositor exists. The sheet's transport and trust boundary are specified in R9.
- A `vaikor-view` crate. None exists. This stub does not add one.
- The Wayland compositor (VKR-L8). Smithay is the native example. It is not a hosted deliverable.
- Grants, the plan verifier, and the Privacy Gateway.

## Hosted approval transport and threat model

Start a run or guard with `--approve unix:/run/vaikor/approval/control.sock --approve-uid <uid>`. The approver uid is mandatory and has no default (R9). The operator (root) provisions only the directory `/run/vaikor/approval/` as specified in R9c; the Core validates it and its ancestors, binds the socket itself with umask 0117 in the setgid (2750/2710) directory, verifies it with `fstatat(AT_SYMLINK_NOFOLLOW)` (socket, core:approver, 0660) before `listen`, and otherwise unlinks the entry it just bound and refuses; the umask is saved and restored around `bind` in the single-threaded startup phase (R9c). The directory lives on tmpfs and is re-created by the operator at every boot (R9c). Existing socket paths are refused rather than overwritten. Use a fresh socket path or remove a previous socket after its Core exits.

An approver connects to the Unix socket and sends one newline-terminated command per connection. `request\n` returns the current binding as a JSON object (`step`, `capability`, `args_digest`, `nonce`, `plan_digest`), or JSON `null` when no approval is pending. For a first-use or over-limit remote model call (R9b), the object also carries `scope` = `{"standing": true, "provider", "task_type", "limit": {"calls", "budget"}, "expiry"}` and `scope_digest` (SHA-256 hex of the RFC 8785 JSON of `scope`). The approver MUST recompute `scope_digest` from `scope` and show the scope before answering. The approve line then carries it as the seventh token after `approve`. A response whose `scope_digest` is missing or differs from the request's is at most a single-call approval and MUST NOT create a standing approval (vectors `approval/standing-binding.json`). Send the bound approve/deny line or `kill\n` on a new connection; an accepted command receives `ok\n`. Acceptance into the queue does not mean the step was approved: the Core checks the binding and deadline. Only the authenticated socket channel receives the nonce. Approver clients must also avoid logging it. The supplied `<who>` is informational; audit actors are fixed by the channel rather than trusted from the response.

A same-uid channel would **not** isolate the Core from other processes running as that uid: a same-uid process could obtain the pending request and approve it, and a TTY can be driven by a same-uid agent through a PTY. R9 therefore allows only the socket channel, refuses same-uid approval, opens no listening socket in local mode (R9 amendment), and R9c requires that no non-approver uid (agent, launcher, worker, model) can switch to the approver uid. Unix permissions and peer credentials do not protect against root, a compromised approver, or a compromised Core.

The legacy `127.0.0.1:port` HTTP bearer approve endpoint is removed in v1, including its routes, its bearer credential file, and its config (`VAIKOR_APPROVAL_SECRET_FILE`); no flag re-enables it. `--approve-uid` and `vaikor kill` use only the Unix socket channel.

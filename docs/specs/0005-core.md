# 0005 – Core contract (VKR-L5)

> **Status:** Draft for approvals, the kill switch, and the hosted audit file (sections 2 and 3). Offline mode and adaptation remain stubs.
> **Date:** 2026-10-15
> **Spec:** VKR-L5 Core Contract
> **Basis:** [VISION.md](../vision/VISION.md) sections 3, 4, and 5, and the security invariants in [0000-architektur.md](0000-architektur.md).

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as in BCP 14 (RFC 2119 and RFC 8174) when they appear in capitals.

The Core is the deterministic part that decides. The model proposes. This layer is the contract for that decision: approvals, the kill switch, the audit log, offline mode, adaptation, and accessibility.

## 1. Decision

**R1.** The model MUST NOT authorize an effect. It MAY propose a plan or a view. The Core decides, after verification and a grant check. *Rationale: invariant 1. A planner output is data.*

**R2.** The Core MUST verify external input before any other check reads fields of that input. Residency, cost, and approval flags are such checks. *Rationale: invariant 3. The hosted guard verifies the plan before residency reads its fields.*

## 2. Approval and kill switch

**R3.** A consequential step MUST NOT run until a human approval arrives on the Trusted UI channel the Core owns (VKR-L4, R8–R12). The approval MUST be bound to the step id, capability, SHA-256 digest of the canonical JSON arguments, the plan digest (0013 R2: SHA-256 of dCBOR, unpadded base64url), and a fresh Core-generated single-use nonce, all echoed by the response (0004 R9). A response for a stale nonce MUST be audited and discarded while the Core keeps waiting for the current nonce until the deadline. A mismatch in a current-nonce response, a replayed nonce, or a timeout MUST be a denial and MUST be audited with its reason and binding digests. The hosted runtime's only channel is the authenticated Unix socket (`--approve unix:<path>`, server-side `SO_PEERCRED` on every connection, 0004 R9); there is no TTY channel. Without it, the step is denied. In local mode there is no approval channel, so consequential steps are denied (`VAIKOR_LOCAL=1`: no listening socket (0 bind/listen), no egress, at most one outbound connect to the statically configured local model endpoint, 0004 R9 amendment); `--approve unix:` with local mode refuses to start (0004 R9 amendment). Offline capability (invariant 7) is not local mode: normal mode with a local `AF_UNIX` approval socket and no egress (no network, or the gateway with no reachable destination, which fails closed per 0007 R3) is fully offline-capable; local mode is the profile with no listening socket and only the local model connect, without consequential steps. The approver uid MUST differ from the Core's and every non-approver uid's (launcher, agent, worker, model/llama) effective uid; same-uid approval is never valid (0004 R9 amendment, R9c). Same uid is not operator-bound: a TTY channel would let an agent under the same uid drive it through a PTY and approve itself, which would violate invariant 4; that is why no TTY channel exists. *Rationale: invariant 4. `approval: true` on a plan is the flag the verifier requires. It is not the human approval.*

**R3a.** The only exception to R3 is the standing approval for remote model and planner calls (0004 R8a, spec 0007 R8a; owner decision, roenu, 2026-10-15). Its first approval and every call over its limit follow R3 **and** 0004 R9b: the request shows and binds the standing scope and its `scope_digest`, and a standing approval exists only if the response echoes that digest. Without it, the response approves one call only. Every other consequential step needs a fresh approval.

**R4.** The owner MUST be able to stop the runtime with a kill switch the Core owns. A generated view MUST NOT be the only control that can stop it. *Rationale: the vision puts the kill switch in the Core contract so a view cannot hide it.*

**R3b.** *Unclear R9c checks fail closed (lead decision D1, 2026-10-16, to be noted as a lead decision in the ratification record).* The Core parses `/etc/sudoers`, `/etc/sudoers.d/*`, and `/etc/doas.conf` itself (0004 R9c). A rule file that is present but unreadable to the core uid, or a rule the Core cannot evaluate clearly, makes the sudo/doas check *unclear*, and an unclear check refuses the approval channel. Only `--operator-attest` lets the channel start in that case; every approval is then audited as `approval_binding=operator-attested`, alongside `attestation=R9c` and the list of what R9c does not detect. **Consequence for the v1 DoD demo:** on a standard Debian host `/etc/sudoers` is mode 0440 root:root, so a non-root Core cannot read it. The demo therefore needs either (a) a host (or container) with no sudo and no doas rule files, or (b) `--operator-attest`, with the operator's R9c attestation on record. A missing sudo or doas binary alone is no switch path and is not unclear.

## 3. Audit log

**R5.** The Core MUST append an audit record for every effect and for every denial, including a refused or timed-out approval. *Rationale: invariant 9 is gapless. A denial that returns an error and writes nothing leaves a hole.*

**R5a.** *Audit before effect (lead decision 2026-10-23, ROADMAP 11e).* The Core MUST durably append the decision for a step (allow, deny, approval outcome) before it calls the step's executor, and the outcome after the effect. If the decision append fails, the step and every later step MUST NOT run. If the outcome append fails, later steps MUST NOT run and the result MUST say the outcome is unaudited. The audit chain MUST be opened and verified before the first step. *Rationale: invariant 9 and the promise "if recording fails, nothing happens"; a record written after the effect leaves a gap whenever the write fails or the process dies in between.*

**R6.** An audit record MUST NOT state that a step was allowed, or that an approval happened, unless that is what the Core did. A consequential step that did not receive an approval on the Trusted UI channel MUST NOT be logged as allowed. *Rationale: a log line that says allow for a step nobody approved asserts a fact the Core did not establish. The hosted executor logs `decision: allow` for every step it runs, including consequential ones. That does not meet this rule. Phases 13 and 14 close it.*

**R7.** Each audit record MUST be chained to the previous record by a cryptographic hash, and the Core MUST be able to verify that chain. The hosted file is append-only. Each line is `previous-hash signature payload`. The signature is Ed25519 over `previous-hash.payload`. The next previous-hash is SHA-256 of that line. `vaikor log verify <file> --public <hex>` checks the chain and the signatures. A changed byte MUST fail verification, and the file MUST remain. *Rationale: invariant 9. A list in memory cannot be checked after restart.*

## 4. Offline, adaptation, accessibility

**R8.** Local mode MUST perform no egress and MUST keep working with no network. `VAIKOR_LOCAL=1`: no listening socket (0 bind/listen), no egress, at most one outbound connect to the statically configured local model endpoint. The model endpoint is `AF_UNIX` by default, with an `SO_PEERCRED` check against the configured model uid; if that endpoint fails, the model connect is refused (fail-closed). `127.0.0.1:<port>` is used only when the operator explicitly configures it (`model.endpoint` set to a TCP loopback address); the Core never falls back to it automatically, and the audit start record marks it. Risk of that fallback: prompts, including `local-only` data (0007 R9), go to whatever local process holds the port, with no peer check. Integrity still holds because model output stays untrusted (schema/GBNF) and every tool call still goes through grant, Cedar, and approval, so a fake endpoint cannot cause any effect without a grant. Verification: an strace test of `VAIKOR_LOCAL=1` MUST show 0 bind/listen, at most one connect in total, and only to the configured endpoint; with an `AF_UNIX` endpoint, no `AF_INET`/`AF_INET6` connect at all. Outside local mode an `AF_UNIX` model endpoint with the peer-uid check MAY also be used; it is not egress, and TCP loopback stays local-mode only (0004 R9d). *Rationale: invariant 7. A planner that can only reach a remote provider is not local mode.*

**R9.** Adaptation (preferences the local router model learns) MUST NOT authorize an effect. A preference is data. Leaving the device with it still requires a grant and the Privacy Gateway. *Rationale: the vision puts adaptation in the Core contract, and the model is not the security boundary. The store for those preferences is the Record primitive. The records phase specifies it. This stub does not.*

**R10.** Core-owned surfaces MUST meet the accessibility rules in VKR-L4 (WCAG 2.2 AA, target size, reduced motion and transparency). *Rationale: the vision lists accessibility in the Core contract. The measurements live in L4 so there is one set.*

## 5. Out of scope

- The Trusted UI drawing rules (VKR-L4).
- Token shape and Cedar grant checks (VKR-L2). Presenting a verified token at execution is roadmap phase 12.
- A graphical Trusted UI. The hosted commands in `0004` are the channel.
- The on-device ensemble (embedding, router/personal, builder). [0009-models.md](0009-models.md) names the roles. The hosted OpenAI-compatible planner is not that ensemble.

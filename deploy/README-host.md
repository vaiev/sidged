# Vaikor on a Debian/Ubuntu host

Status: turnkey work package (c). Bare-host path for Debian 13 and Ubuntu 24.04. The OCI image + compose path
of the v1 spec is separate. 0010 (deployment) is still a stub; this is not a ratified installer.

## Install

```
git clone <your vaikor checkout> && cd vaikor
scripts/install-vaikor-host.sh --dry-run   # print every step
scripts/install-vaikor-host.sh
```

Run it as your admin user, not as root. It installs build dependencies only, builds with the toolchain from
`rust-toolchain.toml`, installs `/usr/local/bin/vaikor`, creates the users `vaikor` (Core) and
`vaikor-approver` (a nologin system account, 0004 R9c), the approval directory `/run/vaikor/approval` (2750 `vaikor:vaikor-approver`,
re-created at boot by tmpfiles.d), `/var/lib/vaikor` (0700), and the audit log key
(`/var/lib/vaikor/log-key/issuer.key`, generated by `vaikor keygen` as `vaikor`). It installs the template
`vaikor-run@.service` and enables nothing. No listener is configured.

## Run

- Scenario: `/var/lib/vaikor/scenarios/<name>/` (`config.json`, `tools.json`, `policy.cedar`, `grant.json`,
  `stub-plan.json`), grant keys: `sudo -u vaikor vaikor keygen /var/lib/vaikor/keys`.
- One run, local profile (default: no network, AF_UNIX only, no approval channel, consequential steps
  denied): `sudo systemctl start vaikor-run@<name>`; output: `journalctl -u vaikor-run@<name>`.
- Egress profile: copy `/usr/local/share/vaikor/systemd/egress.conf.example` to
  `/etc/systemd/system/vaikor-run@<name>.service.d/egress.conf`, fill in the approver and non-approver uids,
  set `VAIKOR_API_KEY_FILE` to a 0600 key file under `/var/lib/vaikor/credentials/`
  (0700, owned by `vaikor`, separate from scenario state), `systemctl daemon-reload`. Approvals come
  from a human-operated client running under the separate approver uid over the Unix socket only
  (0004 R9). The operator must explicitly arrange that client; the installer enables no login shell.
- Verify the audit log: `vaikor log verify /var/lib/vaikor/audit/<name>.log --public <hex>` (the public key
  from `vaikor-tui log-pubkey`).

## Hardening

The unit runs as `User=vaikor` (a stable uid; R9c needs it to own the approval directory, so not
`DynamicUser`) with `NoNewPrivileges`, an empty capability set, `ProtectSystem=strict`, `ProtectHome`,
`PrivateTmp`, `PrivateDevices`, `PrivateNetwork` (local profile), `RestrictAddressFamilies`, `IPAddressDeny=any`
(local profile), `RestrictNamespaces`, `MemoryDenyWriteExecute`, `SystemCallFilter=@system-service` and the
kernel/clock/hostname protections. The egress profile lifts only the network directives: systemd IP filters
cannot name hosts, so the Privacy Gateway registry (0007 R3) stays the control for where bytes may go.

Not verified here: a run on fresh Debian 13 and Ubuntu 24.04 VMs (`ss -tlnpx` showing only the approval
socket during a run, `vaikor log verify`, the R9c start check).

## Planner approvals

Remote planning first asks on the existing approval socket. The request shows a standing scope for the
configured provider and Core task type `planner`, with a call-count limit and the grant expiry. The
count is the grant's message limit, or one call when no message limit is declared. The approver must
recompute the canonical scope digest and echo it to authorize standing use; a plain answer permits
only the current call. `vaikor-tui approve` displays and checks that scope before asking the human.

Standing approvals and their counters are Core control state in the signed audit chain, under its
exclusive lock, separate from data Records. Reusing another audit chain requires first-use approval
again. Each call books its counter before transport; failed calls remain booked. An exhausted scope
prompts for every additional call without resetting its limit. Guard does not retry provider requests
under a single reservation and approval. The Core checks the exact outgoing body with the existing
anonymization checks on every call and durably records the R13 result before reading a credential.

On the authenticated approval socket, `revoke <approval_digest>` revokes one standing approval and
`revoke *` revokes all of them. The digest is the signed approval entry's digest in the control state.
`kill` also revokes all standing approvals and denies further calls. Revocations are appended before
another call can proceed; an audit append failure refuses the call.
